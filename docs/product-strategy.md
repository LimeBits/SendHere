# SendHere（传到这）产品策略与 MVP 建议

> 版本：0.1  
> 状态：产品方向讨论稿  
> 更新日期：2026-08-25

## 1. 核心结论

SendHere 的需求真实，但“局域网传文件”本身已经是成熟且竞争激烈的能力。

产品不应定位为另一个局域网文件传输工具，而应聚焦于：

> **手机扫码，把文字、链接、照片和文件直接传到这台电脑。**  
> **不用登录，不装手机 App，不经过云端。**

更准确地说，SendHere 是：

> **面向手机与电脑的、本地临时剪贴板 + 文件投递箱。**

其中：

- **文本、链接**是高频日常入口；
- **照片、文件**是关键刚需能力；
- **扫码、免安装、无账号、局域网直连**是降低使用门槛的核心手段。

---

## 2. 要解决的用户问题

用户在手机和电脑之间临时传递内容时，常用微信文件传输助手、邮件、网盘、数据线或系统生态工具。

这些方案常见的摩擦包括：

- 需要登录账号；
- 内容经过第三方服务器或云端；
- 文件与聊天记录混在一起，难以管理；
- 传一段文本或一个链接的操作步骤过多；
- Windows 与 iPhone 之间缺少接近 AirDrop 的自然体验；
- 在临时场景中，要求手机安装 App 的成本过高。

### 高频文本场景

文本互传不是文件传输的附属功能，而是一个独立、高频的痛点。

典型场景包括：

- 手机把验证码、地址、订单号发送到电脑；
- 手机把链接、文章、商品页、地图位置发到电脑；
- 手机把 AI 对话、提示词、代码片段、备忘录发送到电脑；
- 电脑把会议链接、网页链接、命令、地址发送到手机；
- 用户希望把手机复制的一段文字立即交给当前电脑；
- 用户不想为了一个短文本打开微信、邮件或网盘。

---

## 3. 目标用户与首要切口

### 核心目标用户

- 同时使用手机和电脑的人；
- Windows + iPhone 用户；
- Windows + Android 用户；
- Mac + Android 用户；
- 家庭、办公室中的多设备用户；
- 希望避免使用微信或云盘中转内容的用户。

### 建议的首要市场切口

> **Windows 与 iPhone 之间，最轻量的 AirDrop 替代方案。**

原因：

- iPhone 与 Mac 已有 AirDrop；
- Android 与 Windows 已有 Quick Share、Phone Link 等选择；
- Windows 与 iPhone 的临时传输体验仍不自然；
- 这一组合的用户更容易感知“扫码即传、无需安装手机 App”的价值。

产品本身仍应支持 macOS 与 Android，但首屏文案、宣传内容和早期用户访谈可优先围绕 Windows + iPhone 展开。

## 4. 竞品与差异化

### 4.1 LocalSend、LANDrop、KDE Connect 等

这些产品通常具备：

- 局域网传输；
- 无账号或低账号依赖；
- 文件、图片、文字传输；
- 跨平台支持；
- 部分支持自动发现、设备配对。

它们的限制或使用门槛通常是：

- 多数需要两端安装 App；
- 产品偏工具化；
- 初次配对、设备发现或权限设置会增加操作；
- iPhone 使用体验可能不如扫码网页直接。

**SendHere 的差异化方向：**

- 电脑安装一次；
- 手机无需安装；
- 扫二维码即连接当前电脑；
- 专注临时传输，而非复杂的长期设备协同；
- 强调本地网络直连与不经云端；
- 将文字和链接体验提升为一等能力。

### 4.2 PairDrop / Snapdrop

这类产品基于浏览器，通常让双方打开网页后自动发现设备并传输内容。

**SendHere 的差异化方向：**

- 以电脑端 App 作为稳定的本地服务与接收中心；
- 手机端通过二维码获得明确的连接目标与授权；
- 使用短期 token 限制访问；
- 不要求用户理解设备发现、房间或配对概念；
- 让“我现在要传给这台电脑”的路径更短。

### 4.3 轻松传（easychuan.cn）

轻松传是一个面向浏览器的跨设备传输服务，公开内容提到文件、文本、屏幕、音视频以及“我的互传”等能力；其站点也提供登录、注册、会员升级和流量购买入口。

它与 SendHere 解决的是同一个大问题：**跨设备传递内容**。但二者的路径不同。

| 维度 | SendHere | 轻松传 |
| --- | --- | --- |
| 核心形态 | 桌面 App + 手机网页 | 纯网页服务 |
| 网络路径 | 同一局域网内直连 | 更偏互联网服务 / 个人传输空间 |
| 公网依赖 | 不需要 | 需要访问其网站与服务 |
| 账号 | MVP 不需要 | 提供登录、注册与会员入口 |
| 典型场景 | 当前手机与当前电脑即时互传 | 跨网络、跨时间、多设备的内容中转 |
| 隐私主张 | 内容不经过 SendHere 服务器 | 用户需要信任其服务端与存储策略 |

可以用一句话区分：

> **轻松传像跨设备的网页中转站；SendHere 应该像 Windows/iPhone 间的本地 AirDrop。**

轻松传证明了跨设备文本和文件传输存在需求；但 SendHere 不能仅复制其“网页传输”能力，应突出 **本地直连、无账号、手机免安装、面向当前电脑即时投递**。

## 5. 产品体验原则

### 5.1 最短核心路径

```text
打开电脑端 → 手机扫码 → 直接发送
```

用户第一次使用时，应尽量在一分钟内完成：

```text
电脑打开 SendHere → 手机扫码 → 手机发送一张照片或一段文字 → 电脑收到并打开/复制
```

### 5.2 文本优先，但不做自动同步

推荐将文本能力设计成“主动式本地临时剪贴板”：

```text
电脑复制文字 → 点击「发送剪贴板文本」 → 手机实时收到
手机输入或粘贴文字 → 点击「发送到电脑」 → 电脑通知并可一键复制
```

第一版原则：

- 只在用户主动点击后读取和发送剪贴板文本；
- 不自动监听、不后台同步系统剪贴板；
- 避免意外传输密码、密钥、隐私内容；
- 连接会话结束后，默认不长期保留文本内容；
- 提供一键清空会话内容的入口。

### 5.3 内容类型应有对应操作

| 内容类型 | 建议呈现与操作 |
| --- | --- |
| URL | 显示「打开链接」 |
| 纯文本 | 显示「复制」 |
| 多行文本 | 保留换行，支持「复制」「保存为 TXT」 |
| 代码片段 | 等宽字体显示，支持「复制代码」 |
| 图片 | 直接预览；iPhone 提示长按保存到照片 |
| 普通文件 | 文件名、大小与「下载」 |

### 5.4 隐私与安全表达

产品首屏和连接页应让用户明确理解：

```text
无需登录
手机无需安装 App
数据仅在当前局域网设备之间传输，不上传云端
```

技术实现必须与文案一致：

- 传输内容不通过产品自有公网服务器；
- 每次启动生成高随机度临时 token；
- token 默认 30 分钟过期；
- 关闭桌面端后 token 立即失效；
- HTTP、WebSocket、文件下载链接均校验 token；
- 支持刷新二维码与撤销已连接设备；
- 避免在日志中持久记录 token 或传输内容。

## 6. 正式技术决策

### 6.1 技术栈

SendHere 的主产品实现正式采用以下组合：

```text
桌面客户端：Flutter + Dart
本地传输服务：Dart `dart:io` + Shelf + shelf_web_socket
手机端：随桌面 App 内置的 HTML / CSS / Vanilla JavaScript 网页
```

架构边界：

```text
Flutter 桌面 UI（macOS / Windows）
  ├── 展示二维码、地址、连接设备、传输记录和发送入口
  └── 启动 Dart 本地 HTTP / WebSocket 服务

Dart 本地服务（0.0.0.0）
  ├── 提供手机网页静态资源
  ├── 校验临时 token
  ├── 接收文字和文件
  ├── 提供临时文件下载
  └── 用 WebSocket 推送实时事件

手机网页（iPhone Safari / Android 浏览器）
  ├── 扫码即打开，不安装 App
  ├── 原生浏览器文件上传与下载
  └── 使用 WebSocket 更新内容和状态
```

手机网页第一版不使用 Flutter Web。页面功能简单，原生 Web 的首屏加载、iPhone Safari 兼容性以及文件上传/下载行为更可控。页面资源必须打包进桌面 App，不能依赖公网 CDN 或外部服务。

### 6.2 平台策略

| 阶段 | 平台 | 实现 |
| --- | --- | --- |
| V1 | macOS、Windows 桌面端 | Flutter Desktop |
| V1 | iPhone、Android 手机浏览器 | 内置原生 Web 页面 |
| V2 | Android、iOS App | Flutter，复用 Dart 协议、模型与服务逻辑 |
| V3 | Linux、鸿蒙等 | 按 Flutter 平台能力扩展 |

不使用 SwiftUI 作为 SendHere 的主产品实现。此前从 RightHere 派生的 Swift/Xcode 工程仅用于验证可复用的 macOS 打包经验，后续不作为业务主线。

### 6.3 初始依赖

```text
Flutter / Dart：
- shelf：HTTP 路由与中间件
- shelf_web_socket：WebSocket
- qr_flutter：二维码
- file_selector：原生文件选择
- path / path_provider：接收目录与文件管理
- shared_preferences：非敏感设置
```

## 7. MVP 范围与优先级

### P0：扫码连接与文本/链接互传

**桌面端**

- 启动局域网 HTTP / WebSocket 服务；
- 显示设备名、局域网地址、二维码、token 剩余时间；
- 展示已连接设备并支持断开；
- 接收手机文本，提供桌面通知和一键复制；
- 手动读取并发送当前剪贴板文本；
- URL 自动识别与打开链接操作；
- 会话内的简易文本记录与一键清空。

**手机网页**

- 扫码后进入授权页面；
- 显示当前连接的电脑名称；
- 输入或粘贴文本并发送；
- 实时接收电脑发来的文本；
- 支持复制与打开链接。

### P1：图片互传

- 手机选择图片发送到电脑；
- 电脑选择或拖拽图片发送到手机；
- 手机网页直接预览图片；
- iPhone 显示长按保存图片的引导；
- 电脑端支持打开图片和打开接收文件夹。

### P2：任意文件互传

- 手机通过 `multipart/form-data` 上传文件到电脑；
- 电脑将文件作为带 token 校验的临时下载资源提供给手机；
- 展示文件名、文件大小、上传/下载状态；
- 基础失败提示与重新发送；
- 默认接收目录为 `Downloads/SendHere/`，允许用户修改。

### MVP 暂不做

- 自动剪贴板同步；
- 账号系统；
- 公网中转与云端历史；
- 手机原生 App；
- 多设备自动发现；
- 文件夹同步；
- 大文件断点续传；
- 多人聊天室；
- 复杂传输统计；
- 长期历史记录。

## 8. 技术与体验风险

### 局域网并不一定可互访

即使设备连接了同一个 Wi-Fi，仍可能因以下因素导致连接失败：

- 企业、酒店或访客网络启用了客户端隔离；
- 防火墙拦截桌面端入站连接；
- VPN 改变路由；
- 多网卡环境选错地址；
- IPv4 / IPv6 网络环境差异。

MVP 应提供：

- 清晰显示当前正在监听的地址和端口；
- 复制访问链接作为二维码失效时的兜底；
- 首次启动时引导系统防火墙授权；
- 端口冲突时自动选择可用端口；
- 易理解的连接失败诊断；
- 明确提示两台设备需要连接同一 Wi-Fi。

### iPhone 浏览器限制

iOS Safari 支持文件和图片上传，但后台、内存、下载与保存相册的行为存在限制。

建议：

- 图片在网页内直接预览；
- 明确提示通过长按图片保存到相册；
- 普通文件使用「下载到文件 App」的心智；
- 对上传失败提供清晰反馈和重试；
- MVP 不承诺大文件后台传输与断点续传。

### HTTP 与 HTTPS

第一版使用局域网 HTTP 可避免自签名证书导致的浏览器安全警告，但局域网中传输内容与 token 并非 TLS 加密。

建议：

- 仅面向可信局域网使用；
- 使用足够随机且短时有效的 token；
- 禁止未授权请求访问传输资源；
- 后续版本再评估设备配对密钥、局域网证书或端到端加密方案。

## 9. 验证指标与用户访谈

### 建议的 MVP 体验指标

| 指标 | 初始目标 |
| --- | --- |
| 首次扫码连接完成时间 | 小于 20 秒 |
| 打开电脑端至完成第一张照片传输 | 小于 1 分钟 |
| 同一可互访 Wi-Fi 下的连接成功率 | 大于 95% |
| 10 MB 图片传输时间 | 正常局域网条件下小于 10 秒 |
| 用户是否理解数据不上传云端 | 通过测试任务与访谈验证 |

### 首轮访谈需要验证的问题

招募 10–20 位目标用户，重点观察：

1. 用户能否不阅读教程完成扫码连接和传输？
2. 用户最常传递的是文字、链接、照片还是文件？
3. 用户是否能理解“手机不需要安装 App”？
4. 用户对局域网直连和隐私主张是否有感知价值？
5. 用户会在哪些场景继续用微信文件传输助手？
6. Windows + iPhone 用户是否愿意用 SendHere 替代现有方法？
7. 用户更倾向于扫码连接，还是愿意后续安装手机 App 换取自动发现？

## 10. 下一步建议

不要先构建完整的跨平台传输体系。优先完成并测试一条完整链路：

```text
Windows 电脑打开 SendHere
→ iPhone 扫描二维码
→ 从相册选择一张照片或粘贴一段文字
→ 电脑实时收到并可打开/复制
```

若这条链路在真实用户手中明显快于微信、数据线、轻松传或 LocalSend，再逐步扩展文件、自动发现和原生 App。

产品成败不在于是否实现 HTTP 上传、二维码与 WebSocket，而在于能否把下面的体验打磨成无需思考的动作：

> **打开电脑端 → 扫一下 → 直接传到这。**
