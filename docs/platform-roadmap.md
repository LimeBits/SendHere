# SendHere 跨平台路线图与网页端改进计划

> 版本：1.0  
> 状态：已确认，作为后续开发与验收依据  
> 更新日期：2026-09-12

## 1. 产品定位与平台边界

SendHere 坚持以下基础约束：

- 仅在当前局域网设备之间直接传输；
- 无账号、无自有云端中转、无 APNs 依赖；
- 文本、图片和文件均应有明确的发送、接收、失败、重试和保存体验。

平台分为两类，而不是让所有端承担相同职责：

| 类型 | 平台 | 目标 |
| --- | --- | --- |
| 原生 App | iOS、Android、macOS、Windows | 高频、可靠、可持续的设备间会话与双向传输 |
| 扫码网页 | iOS Safari、Android 浏览器及常见 WebView | 无安装、临时、快速地向当前电脑投递或接收内容 |

### 原生 App 的统一能力

原生 App 应采用相同的“设备会话”模型：自动发现附近设备、设备在线状态、文本/图片/文件双向传输、传输进度、失败取消重试、未读提醒，以及图片预览和文件保存/打开。

### 扫码网页的范围

扫码网页不追求替代完整聊天 App。它应聚焦于：扫码连接当前电脑、发送文本/拍摄或选择图片/选择文件、显示清晰进度与失败原因、接收电脑下发的文本和下载入口，以及断线后的明确恢复提示。

## 2. 已知问题与共同原则

### 2.1 连接状态必须区分层次

“发现设备”“WebSocket 已识别”“文件 HTTP 上传会话已就绪”不是同一状态。

- 文本可在实时连接建立后发送；
- 文件只有在上传授权与 HTTP 通道就绪后才能投递；
- 文件通道短暂未就绪时，待发送项必须保留为等待状态或在有限窗口内重试，不能直接变为永久失败；
- UI 错误信息应描述用户可行动的原因，不能直接展示底层 `Bad state`。

### 2.2 媒体与文件体验原则

- 图片缩略图和预览始终保持原始宽高比；
- 图片预览、右键/长按菜单、下载或保存入口在各平台语义一致；
- 成功发送的原始文件副本应保留，保证历史消息仍可预览、下载或另存；
- 所有传输均需支持取消、失败信息和重试，不能把中间状态误记为完成。

### 2.3 连接与安全原则

- QR 授权、手机网页会话、桌面 peer 会话应当有明确且相互独立的生命周期；
- 不在日志中暴露可用 token；
- 二维码刷新不得留下“页面显示已连接、HTTP 请求却已失效”的半可用会话；
- peer bootstrap 不应向任意局域网请求无条件签发完整权限 token；
- 服务端应为上传、磁盘空间、临时文件、下载条目设置资源边界与清理策略。

## 3. 开发顺序与验收标准

### 阶段 1：连接与文件传输可靠性（当前优先级）

目标：解决“设备显示在线但文件通道未准备好”导致手机与电脑之间文件发送失败的问题。

实施项：

1. 把 peer 的连接可用状态与文件上传会话就绪状态分开；
2. 仅在文件通道就绪后自动投递待发送文件；
3. 对会话获取中的网络短暂异常进行有限重试；
4. 会话最终不可用时保留可重试语义，避免展示未经分类的底层异常；
5. 添加两台 `LocalTransferServer` 的 loopback 集成测试，覆盖连接、identify、会话创建、上传与重试。

验收：

- 手机和电脑互发图片/文件不会因刚上线的时序而出现“0% 后失败”；
- 临时网络波动后可在合理等待窗口内自动恢复；
- 失败消息说明下一步操作，且待发送内容可手动重试。

### 阶段 2：Android 真机支持

目标：让 Android 成为可靠的原生移动端，而非仅能编译的兼容目标。

实施项：

1. 配置并验证 Release APK；
2. Android 与 macOS/iOS 的文本、相册图片、相机照片、小文件和大文件双向回归；
3. 优先采用系统 Photo Picker，适配 `content://` URI、临时文件生命周期和 Android 10+ MediaStore 保存图片；
4. 处理前后台切换、局域网权限、Wi-Fi 变化与厂商系统限制；
5. 明确文件通道建立中的 UI 状态。

验收：

- 相册选择、拍照、保存图片、打开文件均在真机正常；
- Android 发给电脑与电脑发给 Android 均可完成、取消和重试；
- 没有 Android SDK/真实设备前，不宣称已完成 Android 真机验证。

### 阶段 3：Windows 真机支持

目标：使 Windows 的文件操作、预览、拖拽与网络行为和 macOS 对齐。

实施项：

1. 完成 Windows 10/11 Release 构建与局域网发现、防火墙验证；
2. 收到文件支持打开、资源管理器定位、另存为；
3. 图片支持正确比例缩略图、全屏预览、右键下载和显眼但不过度抢眼的下载按钮；
4. 支持 Explorer 拖入输入区并激活应用窗口；
5. 处理中文文件名、同名文件、长路径及网络类型/防火墙诊断。

验收：

- Windows 与 iOS/Android/macOS 可稳定双向互传；
- 防火墙或网络条件不满足时提供可操作的中文提示；
- 不在没有 Windows 主机测试的情况下宣称已真机验证。

### 阶段 4：网页端核心闭环（优先于网页视觉重做）

目标：恢复并保证“电脑发给扫码手机”的实时收取能力。

实施项：

1. 在 WebSocket 协议中明确区分 `phone` 与 `peer` 角色；
2. 广播仅排除桌面 peer，不能排除已 identify 的手机 socket；
3. 修正手机在线数量与连接状态统计；
4. 添加 identify、重连替换、文字广播和文件通知的端到端测试。

验收：

- 手机扫码并 identify 后，电脑下发文字和文件下载通知均可实时显示；
- 桌面 peer 不会收到面向手机网页的广播。

### 阶段 5：网页端会话、授权与可靠传输

目标：让网页在二维码刷新、弱网、切后台和文件上传中具备可解释、可恢复的行为。

实施项：

1. QR token 仅用于 bootstrap；建立网页会话后与 QR 生命周期分离；
2. QR 刷新时明确保留或撤销旧会话，不能出现半失效状态；
3. token 兑换后从 URL 移除，日志脱敏，下载不再依赖暴露在 URL 中的长期授权；
4. 上传采用临时 `.part` 文件和完成后的原子移动，限制大小、并发、超时和会话配额；
5. 返回结构化错误码，支持单文件重试、取消和字节进度；
6. 下载条目加入 TTL 与清理策略。

验收：

- 中断上传不会留下可见残缺文件；
- 用户能看到哪个文件失败、失败原因并单独重试；
- 刷新二维码后的旧页面行为清晰且一致。

### 阶段 6：网页端事件恢复与移动体验

目标：WebSocket 只作为实时加速通道，不再是消息可靠性的唯一来源。

实施项：

1. 服务端维护有限事件日志、事件 ID 和确认机制；
2. 页面重连携带最后事件游标，补发断线窗口消息；
3. 页面重构为明确状态：扫码连接、已连接、上传中、上传失败、连接断开；
4. 每个文件展示排队、上传中、完成、失败、取消状态；
5. 优化 iOS Safari、Android Chrome 和常见微信 WebView 的安全区、相机/相册选择、焦点和后台恢复；
6. 补齐无障碍语义、焦点态、提交中禁用态和浅色/深色策略。

验收：

- 手机从相机、微信或后台返回后能恢复会话或得到明确重连提示；
- 刷新/短暂断网不再无声丢失电脑下发的文字与文件入口。

## 4. 测试矩阵

每项跨平台功能至少按以下组合验证：

| 发端 | 收端 | 覆盖内容 |
| --- | --- | --- |
| iOS | macOS / Windows | 文本、相册图、相机图、文件、预览、保存、重试 |
| Android | macOS / Windows | 文本、Photo Picker、相机、MediaStore、前后台传输 |
| macOS | iOS / Android / 网页 | 文本、图片原比例、下载/保存、拖拽发送 |
| Windows | iOS / Android / 网页 | 文件操作、图片预览、拖拽、防火墙与网络诊断 |
| 网页 | 桌面端 | 扫码、上传、下载、WebSocket 重连、后台恢复 |

还需覆盖：弱 Wi-Fi、切换 Wi-Fi、电脑睡眠/恢复、空文件、超大文件、同名文件、Unicode 文件名、网络中断、磁盘空间不足以及连接失效。
